# Design: Unified PDF page editor (pdf-arrange)

Generated by /office-hours on 2026-05-22
Branch: master (work branches below)
Repo: ontab / tools
Status: DRAFT
Mode: Builder

Consolidates three Phase 1 tools — `pdf-merge`, `pdf-split`, `pdf-pages` — into a
single page-level editor. Replaces the originally-scoped "migrate pdf-merge" task.

## Problem Statement

Three existing PDF tools (`pdf-merge`, `pdf-split`, `pdf-pages`) are the same
operation underneath: load pages, optionally reorder/rotate/delete, re-assemble.
All three call pdf-lib `copyPages` + `addPage`. Keeping them separate forces the
user to pick a tool before they know what they want, and splits one mental model
across three pages. The weekly real job (combine a bulletin, drop a blank page,
reorder, occasionally split out a section) crosses all three.

## What Makes This Good — the divider primitive

One mechanic unifies all three tools: a per-page **"split after this page" flag**
(the divider). Pages render as a thumbnail grid; the user drags to reorder,
rotates, deletes, and toggles a divider after any page.

| User action | Equivalent old tool |
|---|---|
| 0 dividers active | 1 PDF out = **merge** |
| divider after every page | 1 file per page = **split (all)** |
| dividers after some pages | arbitrary groups = **split (range)** |
| drag / rotate / delete | = **pages (manage)** |
| upload images as pages | partial **image-to-pdf** (bonus input) |

Default is 0 dividers → single merged PDF, so the common case stays dead simple.
Complexity only appears when the user opts into it.

## Scope

**In:** merge, split, page management (reorder/rotate/delete), images as bonus
input pages. One canonical tool `pdf-arrange`. The old slugs `pdf-merge`,
`pdf-split`, `pdf-pages` stay **alive as alias routes** that mount the same tool
(no 301), so their SEO and shared links keep working.

**Out (this consolidation):**
- `image-to-pdf` stays a separate tool. Images are accepted here as a convenience
  input, but the dedicated "images → PDF" entry point and mental model remain.
  (Backlog: it *could* later redirect here too — deferred decision.)
- `pdf-compress`, `pdf-to-image` — unrelated, untouched.
- Raising the global per-file size limit — deferred to backlog (cross-cutting).

## The unified model (data + semantics)

Single ordered list of page items in component state:

```
PageItem = {
  id: string            // stable, for dnd-kit + React keys
  sourceFileId: string  // which uploaded file
  sourceFileName: string// e.g. "filename.pdf" / "imagefile.png"
  kind: "pdf" | "image"
  sourcePageIndex: number // 0-based index within source PDF (ignored for image)
  rotation: 0 | 90 | 180 | 270
  splitAfter: boolean   // divider after this page is active
  // thumbnail rendered lazily, cached by id
}
```

- **Page number**: global 1-based running index over the visible (non-deleted)
  list; recomputed on reorder/delete. (Convention trap h.)
- **Divider = `splitAfter` on the page**, not a positional slot. Reorder moves the
  flag with the page; delete removes it. Last page's `splitAfter` has no effect
  (nothing after it) — not rendered.
- **Delete** removes the item; following pages pull forward (no blank slots).
- **Sections** = contiguous runs of pages bounded by active dividers / list ends.
- **Empty section** (all its pages deleted) is skipped in output.
- **Apply count** = number of non-empty sections = "(n개 파일)" on the apply button,
  computed live.
- **Rotation**: click cycles +90° clockwise (0→90→180→270). Thumbnail reflects it.
- **Output**: always PDF. Images embedded at native size (reuse `imagesToPdf`
  logic). Each section → one PDF via pdf-lib `copyPages`/`addPage` + per-page
  rotation (reuse `rebuildPdf` logic from managePages).

## Screen 1 — Editor

Layout follows the user's wireframe draft (2026-05-22).

**Top strip (below header, image-compress pattern):**
- Uploaded-files info: `{firstName} +N개 파일` + `다시 업로드` (re-pick, replaces).
- `모두 분할` — activate divider after every page.
- `선택 해제` — clear all active dividers.
- `적용 (n개 파일)` — n = live non-empty section count.

**Header:** title "PDF 합치기 / 나누기 / 정렬", subtitle
"여러 PDF를 하나의 파일로 합치거나 여러 파일로 나눕니다."

**Main area:** fixed vertical height (same envelope as other tools), vertical
scroll. Pages laid out in a wrapping thumbnail grid in order across all uploaded
files (PDF + image).

Per-page thumbnail, on hover:
- top-left: page number
- top-right: rotate + delete buttons
- bottom-center: source file name

Drag to reorder (dnd-kit/sortable). Page numbers update to match.

**Divider:** faint line on the right edge of each thumbnail; hover thickens it;
click toggles active (color change). Active = split boundary after that page. In a
wrapping grid the divider sits at the trailing edge of the page's cell (e.g. the
divider after page 5 renders at the end of row 1, right of the 5th thumbnail).

**`+` cell:** after the last page. Click opens the file picker immediately
(same as 다시 업로드). Appends new files/images to the end of the list.

## Screen 2 — Result (after 적용)

Uploaded-files info strip stays. Body splits left / right.

**Left:** prepared output files in a single scrollable column. Each row: first-page
thumbnail, file name, file size (`formatBytes`), download button.

**Right (result card, image-compress pattern):** "적용 완료", count, zip filename,
download button (zip), `다시 선택` button.

- `다운로드` → zip of all output PDFs.
- `다시 선택` → return to editor at the exact pre-apply state (order, dividers,
  rotation, deletions all preserved).

**Single-file case** (no active dividers → 1 section):
- Hide count + zip filename on the card.
- Download is the PDF directly (not zip).
- Left column has exactly one file.

## Output filename rules (Q3 = A)

Let `base` = first uploaded file's name without extension.
- 1 section → `{base}.pdf`
- N sections → zip `{base}-split.zip` containing `{base}-1.pdf` … `{base}-N.pdf`

## Self-host pdfjs (PR1, separate infra PR)

pdfjs currently loads worker + cmaps + standard_fonts from unpkg in
`pdfToImage.ts` and `managePages.ts` (duplicated `getPdfjsLib`). This tool's
lazy per-page rendering makes pdfjs load-bearing, so self-host now:
- Build step copies `node_modules/pdfjs-dist/{build/pdf.worker.min.mjs,cmaps,
  standard_fonts}` → `public/pdfjs/`.
- New shared `src/lib/pdf/pdfjs.ts` exposing one `getPdfjsLib()` pointing at
  same-origin `/pdfjs/...`.
- Refactor `managePages.ts` to use it (its `generateThumbnails` is being absorbed
  into pdf-arrange anyway). `pdfToImage.ts` (still `/pdf-to-image`) migrates to
  the shared helper too, removing the last unpkg consumer.
- cmaps are required for Korean PDF text rendering — must ship, not drop.

## Performance (Q2 = A)

- Lazy thumbnail render: IntersectionObserver (or windowing) renders a page's
  pdfjs canvas → cached blob/dataURL only when scrolled near view. Image pages
  use the source image directly (no pdfjs).
- Thumbnails ~200px wide → ~0.2MB each; off-screen pages hold no bitmap.
- Soft warning at total input > 100MB (sum of bytes). Never blocks. Real OOM
  surfaces via existing `useToolProcessor` `memoryHint`.

## Approaches considered

### Approach A: per-page list + `splitAfter` flag (recommended)
Single `PageItem[]` state, dnd-kit sortable, lazy pdfjs thumbnails, section-aware
assembler. Effort: L (human: ~4-6 days / CC: ~few sessions). Risk: Med (grid +
divider UI, lazy render). Reuses rebuildPdf/imagesToPdf/dnd-kit/result-card.
- Pros: one mental model, covers all 3 tools + image input; common case stays
  simple; matches the wireframe exactly.
- Cons: most complex UI in the project; lazy-render adds plumbing; divider-in-grid
  needs design exploration.

### Approach B: don't unify — silver-migrate pdf-merge only
Original task. Effort: S. Risk: Low.
- Pros: small PR, fits "1 tool = 1 PR" cleanly.
- Cons: abandons the chosen product direction; still leaves split/pages as
  separate future work; three mental models persist.

### Approach C: unify but render all thumbnails upfront
Approach A without lazy render. Effort: M. Risk: Med-High (memory).
- Pros: simpler render code.
- Cons: violates the lightweight principle for large/many PDFs; can OOM.

**Recommended: A.** It's what the user designed, and the divider primitive plus
lazy render keep the complexity and memory honest.

## Editor visual direction (design-shotgun 2026-05-22, approved)

Variant **A — inline edge-mark + section tone band** chosen. Mockups at
`~/.gstack/projects/KOJUNKYUNG-tools/designs/pdf-arrange-editor-20260522/`
(variant-A.html / variant-A-r2.png + approved.json).

- **Continuous wrap grid, no reflow** — most layout-stable (UI stability contract).
  Pages centered (`justify-content:center`).
- **Divider** = thin vertical bar in the gutter at each page's right edge. idle =
  faint hairline (~0.45 opacity), hover = thicker, active = `accent-electric` solid
  + scissors mark. It is the page's `splitAfter`; last page has no divider.
- **Section grouping** = subtle per-page tint ring behind contiguous pages
  (electric / copper / silver, cycled). Wrap-safe because per-cell, not a
  spanning shape.
- **Hover controls** = absolute overlays on the thumbnail (page number TL,
  rotate/delete TR, filename chip bottom) → zero layout shift.
- **`+` add card** at the end; last page has no trailing divider, so reserve an
  18px gap before the add card.
- Row-wrap divider question resolved (edge-mark model sidesteps it).
